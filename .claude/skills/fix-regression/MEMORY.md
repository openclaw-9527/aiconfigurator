# Memory: fix-regression

## Lessons Learned (from autofix run 25088054829)

1. **Verify on `main` before assuming the regression is live.** The `FailedBranch` field in the issue template is often an unreleased tag (e.g. `release/0.8.0`) that does not exist on origin. Start by running `SupportMatrix.run_single_test(model, system, backend, version)` on current `main`. Four of five issues this run were already green on main -- either truly stale (#27), fixed by a later PR that needs cherry-pick (#28), or green-by-coincidence (#29).
2. **`git lfs pull` is a mandatory preflight.** `*_perf.txt` files under `systems/data/<system>/<backend>/<version>/` are LFS-tracked. Missing blobs cause `perf_database.load_*` to silently return `None`, which surfaces as `AttributeError: NoneType` deep in the query path -- completely unlike the advertised failure. Before trusting any traceback, confirm the perf files begin with a CSV header, not `version https://git-lfs.github.com/spec/v1`.
3. **Top-level PASS hides per-candidate exceptions.** `pareto_analysis.agg_pareto` swallows per-parallel-config failures into `exceptions.append(e)`; `run_single_test` returns `True` unless *every* candidate fails. Grep captured logs for `Traceback` / `Error` / `Invalid quantized MoE configuration` / `PerfDataNotAvailableError` even when the boolean result is green.
4. **Pre-filter instead of exception-handle.** Where a computed constraint can prune the sweep upfront (e.g. fp8_block MoE: `(moe_intermediate_size // moe_tp) % weight_block_size == 0`), add a filter in `sdk/utils.py` invoked at the top of `agg_pareto`/`disagg_pareto`. This produces a readable failure when *all* candidates are pruned, rather than a misleading "last exception" message.
5. **Search for prior agent PRs before opening a new one.** Use `gh pr list --state all --search "<symptom>"` and also look for branches named `fix/issue-<N>-*`. A closed-without-comment PR from an earlier agent run is a strong "human rejected this" signal -- post findings and ask for human direction on the issue instead of re-submitting.
6. **Data-coverage fixes can mask latent validator bugs.** If the reported symptom no longer reproduces on main, identify *why* -- added perf rows, renamed enums, cherry-picked fix -- and call that out when closing. Otherwise the underlying bug (e.g. dense-model fp8 MoE validator in #29) will resurface on the next backend/system that lacks that coverage.
7. **Nested-`defaultdict` lookups in `perf_database.py` are an accident surface.** `query_custom_allreduce` (fixed by #884) and `query_moe` (fixed by #32 this run) both had the same empty-leaf `IndexError` trap. When touching one `query_*` method, sweep the others for the identical pattern.
8. **Distinguish code-regression-on-release from missing-data.** An assertion like `values is None or len(values) < 2` in `_nearest_1d_point_helper` often indicates `min(tp_size, N)` clamping to a key with no rows, not missing data. Check the caller's clamping logic and whether the CSV has rows at the clamped tp_size before recommending a collection run.
9. **GB200 single-node cap is `num_gpus_per_node=4`.** `custom_allreduce_perf.txt` only has `num_gpus=2,4` rows by design. Larger tp_size values must be handled via clamp-and-rescale in the query path (PR #681), not by collecting more rows.
10. **Cherry-pick, don't re-fix, when main already has the fix.** If commit X on main resolves the release-branch failure, a cherry-pick is the right answer -- no new PR against main. Post the commit SHA and author on the issue so the release owner can act.
